## PR, merge and conflict handling

- Branch per phase off the latest `origin/master`. Commit explicit paths with clear messages. Push with `git push -u origin <branch>`, retrying up to 4 times with backoff on network errors.
- Open a PR (follow any PR template in `.github/`). The body states: what changed, the verification output, the SEO diff summary, and any whitelisted title, H1 or meta changes.
- Wait for CI. If it is red, root-cause, fix and push. "Flake" is not a root cause. Never skip or disable a check.
- Review comments: fix the small ones and push; reply on the larger ones with a proposal.
- Merge conflicts: merge `origin/master` into the branch, regenerate HTML with `node build-site.mjs` (never hand-merge generated HTML), re-verify, push. No rebase or force-push on shared branches.
- **Merge only when** CI is green, verification passes locally, and there is no open blocking comment. Merge commits.
- **After every merge = deploy:**
  - wait for Hostinger (up to about 10 min)
  - run `BASE=https://tasacion.com.py node tools/seo-audit.mjs` → `seo-diff` against the pre-merge local audit
  - `curl` 3 pages and grep for the new number and the absence of the old one
  - open one WhatsApp link at 390 and check the prefilled text
  - check the 8 legacy URLs still 301
  - if `site.css` or `site.js` look stale, ask Anton to purge the Hostinger CDN (hPanel → Performance → CDN → Purge)
  - if live does not change, stop merging and report the deploy-branch blocker
